# Redis 离线消息

Redis 离线动作按接收客户端维护多条消息，系统负责消息结构、顺序索引、过期检查和确认清理。动作只需选择数据源并设置过期时间，不填写 SQL、Redis 命令、key 或消息模板。

## 前提条件

- 接收设备先建立持久会话并订阅目标主题；MQTT 3.1.1 使用 `Clean Session=false`，MQTT 5 设置有效的 Session Expiry Interval。
- 订阅已生效且通过 ACL，设备离线时会话尚未过期。
- 投递 QoS 为 1 或 2。QoS 0 不进入外部离线存储。
- 数据源连接可用，启用了相应 OFFLINE 规则。

首次接入、没有历史订阅的设备，不会仅因其他设备向某主题发布就自动产生其离线消息。

## 控制台配置

1. 在「数据源」创建 Redis 连接，填写连接地址、数据库及连接池参数。
2. 在「规则引擎」新增规则，数据类型选择「离线」。
3. 保留 SQL `SELECT * FROM "$EVENT.OFFLINE"`。
4. 添加「写入离线消息 / Redis」动作，选择 Redis 数据源。
5. 设置过期时间，例如 `3600` 秒，保存并启用。

动作配置示例，`source_name` 替换为实际数据源标识：

```json
{
  "id": "offline-redis-action",
  "action_type": "OFFLINE_REDIS",
  "source_name": "redis-offline",
  "expire_time": 3600
}
```

`expire_time=0` 表示不额外设置动作过期时间，仍受 MQTT 5 Message Expiry Interval 约束；两者同时存在时取较早的截止时间。

## 多条消息的存储结构

信箱由规则 ID、动作 ID、接收客户端 ID 共同确定。键前缀为 `velamq:offline:v1:{digest}`，`digest` 为这些标识计算的摘要。

| 键后缀 | Redis 类型 | 内容 |
| --- | --- | --- |
| `:messages` | Hash | 应用消息 ID → 完整消息二进制记录 |
| `:order` | Sorted Set | 递增序号 → 应用消息 ID |
| `:expiry` | Sorted Set | 到期时间 → 应用消息 ID |
| `:meta` | Hash | 序号及占用字节统计 |

不会用单个 `SET client_id payload` 覆盖同一设备的旧消息。Lua 脚本维护消息、索引、容量及确认删除的一致性，批量写入使用 pipeline。内置信箱是内部格式，请勿手动改写其中某一个键。

## 设备如何取回消息

1. 使用相同 Client ID 恢复持久会话；已有订阅可直接恢复，无需额外的业务拉取接口。
2. 新增订阅时，在权限检查和路由同步成功后触发匹配消息补发。
3. Broker 分页读取信箱，默认每页 32 条；只补发当前有效订阅匹配的消息，并受会话队列容量限制。
4. 读取不删除记录。QoS 1 收到 PUBACK 后删除对应消息；QoS 2 等到 PUBCOMP，PUBREC 不删除。
5. 部分确认后断线，未完成确认的消息保留，下次重连继续补发。客户端仍应按 MQTT 重投递语义去重。

## 容量、故障与运维

单客户端存储受会话 `max_queued_messages` 和 `max_queued_bytes` 限制；超限按内置策略淘汰最旧记录。容量不足、到期以及数据库故障均需监控，不能把 TTL 配成 0 理解为无限容量。

未配置外部离线动作、外部保存队列满或写入失败时，会使用原生有界队列作为回退。外部保存是异步的，发布端 ACK 不是 Redis 落盘确认；Redis 自身的持久化、复制和备份需由运维配置。

已知问题：突刺导致原生与外部积压混合后，当前补发可能乱序。严格顺序场景应等待该问题修复。多规则、多动作以及修改信箱标识也会改变补发行为，上线前应测试积压迁移。
