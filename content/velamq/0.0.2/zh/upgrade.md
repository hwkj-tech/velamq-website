# 升级与集群运维

三节点集群可按节点逐个重启，但集群可用不等于每条 TCP 连接不断开。被重启节点上的客户端需要重连；是否恢复消息还取决于会话、QoS、存储副本和客户端参数。

## 升级前

- 记录实际运行版本、配置、节点 ID、数据目录、License 和集群成员。
- 确认三个节点健康、Raft Leader 存在、副本追平，无持续写入错误。
- 备份业务数据和配置；JSON 配置导出不包含会话和消息。
- 确认新旧版本的数据兼容及回退路径。不要把同版本重启通过当作任意跨版本升级已验证。
- 提前处理旧 Redis 自定义离线积压，保留规则及动作标识。

## 逐节点操作

1. 先选一个非 Leader 节点，从负载均衡的新连接入口摘除。
2. 停止该节点服务，保留节点身份及数据目录，替换已验证的程序包后启动。
3. 确认节点重新加入、副本追平、接入/订阅/跨节点投递正常，再恢复入口流量。
4. 重复处理另一个非 Leader；一次只处理一个节点。
5. 最后处理当前 Leader，观察剩余节点多数派选主及客户端重试，再检查恢复节点。

Leader 停止时，两个健康且互通的投票节点通常仍构成三节点集群的多数派，可以重新选主。选举和恢复期间依赖 Leader 的操作可能短暂等待或失败，不能承诺完全无感；如果已存在另一节点故障、分区或副本异常，不应继续滚动操作。

## 恢复检查

检查 MQTT 新连接、SUBACK、跨节点发布订阅、共享订阅，以及持久会话恢复。针对业务启用的保留消息、延迟消息、外部离线消息分别做验证；同时观察 gRPC 错误、Raft 日志状态、积压和进程资源。

需要严格消息顺序时，还应验证突刺和原生/外部混合积压恢复。当前已知该场景存在乱序，不能用单纯「全部条数收到」替代顺序检查。

## 黑白名单与接入

连接准入在设备认证前执行，无启用规则则继续认证；命中黑名单立即拒绝；存在启用白名单时必须命中至少一条。添加第一条白名单前应确认全部合法设备在允许范围内。

支持 Client ID/用户名的精确或正则匹配，以及来源 IP 的精确/CIDR 匹配。运行节点使用编译后的本地内存快照进行判断，不为每个 CONNECT 查询 RocksDB；配置热更新后同步到其他运行节点。

版本号以实际二进制及仪表盘显示为准。本手册不提供未经发布验证的 0.0.2 安装包下载地址。
